Prepare Ferry for deployment on my Fly.io account, and set up a repeatable deploy + feedback loop. Auto-loaded memory (ferry-v0-shipped.md) has the full project state.

THIS IS A NEW WORKSTREAM, NOT Plan 6b. Plan 6b (Firecracker microVM isolation) stays pending as a named concept, but see the recommended direction below — it gets absorbed into this work, not finished separately first. Decision (Robbert, 2026-08-17): deploy the CURRENT working product to Fly.io — deliberately WITHOUT a separate isolation project first — so Robbert can create his account online, couple an online demo WordPress site he controls (provided later), run real tests, and drive a commit → deploy → feedback loop. This is CONTROLLED testing on sites Robbert owns, not a public launch.

**Where the product is.** Plans 1–6a are MERGED to main (latest: merge 4712592, Plan 6a hardening, 2026-08-13). The product works end-to-end LOCALLY: pull a WordPress site into a local DDEV clone, chat with a per-site Claude agent that edits code, push typed changes to production behind one human click, rollback. App shape: `ferry-server` (Fastify + better-sqlite3, tsx runtime) is the one deployable process — it serves the API AND the built `ferry-dashboard` dist. `ferry-plugin` (native PHP) is bundled into the image for `/api/plugin.zip`, not deployed. `ferry-cli` is imported as a library by the server.

**Goal.** (1) Ferry running on Robbert's Fly account (one app = server + dashboard). (2) A repeatable deploy path after every update — decide direct `fly deploy` vs GitHub Actions on push-to-main. (3) Robbert can sign up / log in and couple a demo site. (4) Full observability for the assistant — decide the mix of `fly logs` (app logs to stdout via console.*), `fly ssh console` (inspect the SQLite DB + clone state), optionally a `FLY_API_TOKEN`. (5) The ongoing loop: test → feedback → change, commit, deploy.

**The central hard problem — investigate FIRST, before any deploy.** The clone substrate is local-dev-shaped: the engine creates and runs each WordPress clone as a DDEV project (Docker containers, mkcert TLS, *.ddev.site hostnames, wp-cli, mysqlbinlog); `verifyClone` hits the clone's DDEV URL. None of that exists on Fly by default. A Fly Machine is itself a Firecracker microVM (a full Linux VM). Core design question: run DDEV/Docker inside a Fly Machine, OR replace the clone substrate with a Fly-native approach. Verify against CURRENT Fly docs (context7 / fly.io docs — do not assume).

**Recommended milestone phasing (confirm at brainstorm).** M1 — control plane + dashboard online, account creation works, deploy pipeline + observability proven; no clone/sync/agent yet (small, de-risks the pipeline, not throwaway). M2 — one demo-site clone + sync + agent working on Fly; where the DDEV-on-Fly question is decided, potentially large.

**Recommended direction for M2's clone runtime (Robbert + assistant, 2026-08-17, confirm at brainstorm):** lean toward "one Fly Machine per site" rather than self-hosting Firecracker on a KVM box. A Fly Machine IS a Firecracker microVM, so this delivers the isolation primitive for free and makes M2 absorb most of Plan 6b — no separate Firecracker-ops project. What remains of 6b then becomes design-on-top-of-Fly: default-deny egress at the Machine level, a transparent stub proxy for license endpoints (WireMock/VCR pattern; block + log the rest), and moving the agent-reachable write secret out. Do NOT treat 6b as a prerequisite to finish first; it rides along in M2. Exception: if Robbert intends to onboard real, untrusted third-party sites soon, isolation must be front-loaded — but the stated plan (a demo site Robbert controls) is bounded, so M1-first + isolation-in-M2 is the recommended sequence.

**Concrete changes already known to be needed (handle in the plan).** Bind the server to 0.0.0.0 not 127.0.0.1 (`ferry-server/src/main.ts` ~L77 `app.listen({ port, host: '127.0.0.1' })`). Turn ON the `secure` cookie flag — Plan 6a deferred it to "whichever plan first deploys behind TLS"; this is that moment (`ferry-server/src/routes/auth.ts` COOKIE_OPTS lacks it); env-condition it so local http dev still works. Persistence: the dir `ferryHome()` resolves (holds `server.db` + all clones) is on ephemeral rootfs — it MUST live on a mounted Fly Volume or accounts/sites vanish on redeploy. `ANTHROPIC_API_KEY` as a Fly secret. The image must include `ferry-plugin/` and the built `ferry-dashboard/dist`. 6a graceful shutdown already handles SIGTERM (Fly sends it on deploy) — verify a clean drain.

**Security posture for this phase (state explicitly).** Until M2's isolation lands, the agent holds a host shell on the Machine and the agent-reachable write secret is reachable. Acceptable ONLY because testing is on sites Robbert controls. Do NOT open public signup, and do NOT re-enable agent web tools (WebSearch/WebFetch stay off — prompt-injection vector while the agent holds a host shell). Gate or single-tenant the app.

**Process (same disciplined flow as every plan).** (1) superpowers:brainstorming from this prompt — resolve the forks (clone substrate, deploy mechanism, milestone scope, observability, single-tenant gating) WITH Robbert. (2) design doc → Robbert sign-off. (3) superpowers:writing-plans → sign-off. (4) execute (subagent-driven-development on a fresh branch off main, per-task adversarial reviews; lighter path OK for small pure-ops plans). Keep the gate green: cli/server vitest, plugin phpunit, three typechecks, dashboard e2e.
